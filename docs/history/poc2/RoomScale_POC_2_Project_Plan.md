# RoomScale POC 2 — AI-Assisted Photo → RoomDefinition

## 1. Purpose

RoomScale POC 1 proved the core gameplay fantasy.

RoomScale POC 1.5 establishes that the same civilization simulation can operate against different data-driven `RoomDefinition` inputs without room-specific gameplay code.

POC 2 exists to prove the next boundary:

> Can a capable multimodal AI, given ordinary photographs and a reusable RoomScale reconstruction skill, author a recognizable and playable `RoomDefinition` for a real room?

POC 2 does **not** place a computer-vision model or AI runtime inside the game.

Instead, POC 2 creates a reusable repository skill that teaches an external multimodal AI how to interpret room photographs and produce RoomScale-compatible room data.

The intended pipeline is:

**ordinary room photographs → RoomScale reconstruction skill + multimodal AI → RoomDefinition → validator → RoomScale**

The resulting `RoomDefinition` is an ordinary game input. Once generated, RoomScale runs without requiring the reconstruction AI.

---

## 2. Central POC Question

The primary question is:

> Can a user take ordinary photographs of a room, give those photographs and the repository reconstruction skill to a capable multimodal AI, receive a valid room file, place that file in RoomScale, and see a recognizable version of the photographed room support the existing RoomScale gameplay loop?

Success is determined primarily by:

1. recognizable visual/layout resemblance;
2. valid RoomDefinition output;
3. successful integration with the existing RoomScale simulation;
4. reproducibility from the repository skill without relying on prior conversation history.

Exact surveying-grade reconstruction is not required.

---

## 3. Architectural Principle

POC 2 must preserve the boundary established by POC 1.5.

Conceptually:

**POC 1.5**

`RoomDefinition → RoomScale`

**POC 2**

`photos → AI + RoomScale reconstruction skill → RoomDefinition → RoomScale`

The RoomScale simulation must not know whether a room definition was:

- written by a developer;
- generated by Luna;
- generated by ChatGPT;
- generated by another capable multimodal AI;
- produced by a future photogrammetry/CV pipeline;
- produced by a future room editor.

`RoomDefinition` remains the stable integration contract.

---

## 4. Primary Deliverables

POC 2 must produce:

1. a reusable room-reconstruction skill committed to the repository;
2. supporting schema/reference material required by the skill;
3. documentation explaining the user workflow;
4. any necessary visual/appearance extensions to `RoomDefinition`;
5. a validator/repair workflow suitable for AI-generated rooms;
6. one canonical AI-generated room based on the supplied real-room photographs;
7. automated evidence that the generated room loads and supports gameplay;
8. reproducibility evidence from a fresh AI context;
9. a second-model/assistant test where practical.

---

## 5. Development Constraint

The existing RoomScale autonomy constraint remains binding.

The user must not be required to:

- create or edit Godot scenes;
- manually place walls or furniture;
- manually build navigation;
- manually author traversal anchors;
- repair generated geometry in the Godot editor;
- use Blender;
- write code;
- debug the game;
- manually translate photographs into JSON.

The user may:

- take ordinary room photographs;
- optionally provide descriptive context;
- optionally provide a known measurement;
- copy/place the AI-generated room file where the README instructs;
- invoke the documented validation/run command.

If the generated definition fails validation, the intended repair path is **AI revision using validator feedback**, not manual level editing.

POC 2 depends on POC 1.5 being sufficiently complete that:

- `RoomDefinition` is authoritative;
- Room A and Room B are data driven;
- room validation exists;
- gameplay systems do not contain room-specific target/coordinate logic;

Do not compensate for incomplete POC 1.5 abstraction by adding photo-room-specific gameplay conditionals in POC 2.

If POC 2 exposes a missing general capability in `RoomDefinition`, extend the contract cleanly rather than special-casing the photographed room.

## 8. Flexible Photo Input

The reconstruction skill must not require exactly four photographs.

It must accept a variable-size collection of ordinary images representing the same room.

Examples that should be conceptually supported:

- 2 photographs;
- 3 photographs;
- 4 photographs;
- 8 photographs;
- additional photographs supplied after an initial attempt.

The skill should use all useful visual evidence supplied.

POC 2 does not need to prove reliable reconstruction from every possible image count or image quality.

The key requirement is that the workflow itself not be architected around a fixed four-view template.

## 9. No Special Capture Requirement

The normal reconstruction workflow must not require:

- LiDAR;
- depth cameras;
- AR room scanning;
- photogrammetry rigs;
- 360-degree cameras;
- specialized capture applications;
- predetermined camera coordinates;
- EXIF calibration data supplied by the user.

Such information may be used in future versions if available, but ordinary phone/camera photographs are the required POC input class.

## 10. Optional User Context

The skill may accept optional supporting information.

Examples:

- a known wall length;
- desk height;
- door width;
- approximate room dimensions;
- identification of an ambiguous object;
- clarification that two photos show the same object;
- description of an area hidden in every image.

None of this is mandatory for the canonical test.

A known scale reference may improve absolute dimensions, but POC 2 must not require one.

---

## 11. Reconstruction Priority

POC 2 prioritizes:

1. room recognizability;
2. major layout fidelity;
3. relative proportions;
4. major architectural features;
5. major object placement and resemblance;
6. gameplay-relevant geometry;
7. exact physical measurements.

The reconstruction is not a surveying system.

A visually recognizable room with approximate dimensions is preferable to an unrecognizable reconstruction whose numeric dimensions happen to be accurate.

## 13. Skill Self-Containment

The reconstruction skill must provide enough context for a fresh AI session to perform the task correctly.

At minimum it must explain:

- what RoomScale is;
- what a `RoomDefinition` is;
- what files/images are inputs;
- what output must be produced;
- the required schema;
- coordinate/orientation conventions;
- RoomScale world-unit conventions;
- how to reconcile evidence across photographs;
- how to estimate room shell geometry;
- how to represent objects;
- how to represent visual appearance;
- how to identify navigable surfaces;
- how to represent navigation obstacles;
- how to expose traversal-relevant geometry;
- how to represent uncertainty;
- what must not be fabricated;
- how to validate output;
- how to repair validator failures;
- final checks before declaring completion.

The skill must not depend on private knowledge from the RoomScale development conversation.

---

## 14. AI Role

The reconstruction AI acts as an **author of RoomDefinition data**.

It is responsible for analyzing the supplied photographs and producing the best supported approximation of the room under the skill's rules.

The AI may reason about:

- repeated landmarks across images;
- approximate viewpoint relationships;
- room boundaries;
- object identity;
- relative scale;
- depth ordering;
- object orientation;
- colors/material categories;
- plausible hidden geometry needed to form a coherent object.

The AI must distinguish observed information from approximation where relevant.

---

## 15. Cross-View Reconciliation

The skill must instruct the AI to treat all input photographs as observations of the same physical environment unless told otherwise.

The AI should reconcile:

- the same object seen from multiple directions;
- partial views of one object;
- walls seen from opposite sides of the room;
- repeated doors/windows;
- overlapping furniture;
- consistent relative placement.

A desk visible in three images must normally become one desk object, not three independent objects.

---

## 16. Coverage and Ambiguity

The AI should evaluate whether the supplied photographs provide enough information to create a coherent playable approximation.

If important geometry is uncertain, the AI may:

1. make a conservative approximation when the ambiguity does not materially threaten recognizability or gameplay;
2. mark/document the approximation when useful;
3. request a specific additional photo if the missing information materially blocks a reasonable reconstruction.

The workflow must not require a predetermined capture checklist.

When requesting another image, the request should be actionable.

Example:

> "The left side of the cabinet and the wall behind it are not visible in any supplied view. Please provide one photo from the opposite side of the room showing that wall."

---

## 17. Room Shell Reconstruction

The generated RoomDefinition should contain a coherent approximation of:

- floor footprint;
- enclosing walls;
- wall height;
- ceiling height/room height where represented;
- visible doors;
- visible windows;
- major openings;
- major trim/structural features where they strongly contribute to room identity.

Perfect architectural measurement is not required.

The shell must be coherent enough for RoomScale to render a recognizable room and contain gameplay objects correctly.

---

## 18. Major Object Reconstruction

The reconstruction should focus on objects that materially affect:

- visual room identity;
- floor layout;
- traversal;
- elevated territory;
- gameplay navigation.

Major objects should receive, where applicable:

- stable unique ID;
- semantic type;
- display name;
- approximate position;
- approximate dimensions;
- orientation;
- obstacle behavior;
- elevated/navigable surface information;
- appearance information.

Do not attempt to represent every piece of clutter.

---

## 19. Semantic Classification

The skill should use useful semantic types wherever possible.

Examples include:

- desk;
- chair;
- cabinet;
- dresser;
- bookshelf;
- table;
- shelf;
- door;
- window;
- rug;
- storage container;
- large decorative/structural object.

The data model must remain extensible and must not require a hard-coded exhaustive list of household objects.

---

## 20. Visual Appearance Contract

POC 1.5 primarily establishes simulation geometry.

POC 2 may extend `RoomDefinition` with a small, general-purpose visual-description layer if required to create recognizable reconstructed rooms.

Useful fields may include:

- base color;
- secondary/accent color;
- material category;
- shape/archetype;
- transparency/glass indicator;
- simple style descriptors;
- optional texture/material reference;
- optional generated-asset reference.

Exact schema design is an implementation decision.

Any extension must remain:

- generic;
- inspectable;
- optional where appropriate;
- independent of the canonical photographed room;
- compatible with future room producers.

---

## 21. Recognition Standard

The canonical reconstruction must be recognizably based on the photographed room.

Recognition should come from the combination of:

- room shape;
- wall/opening placement;
- major furniture arrangement;
- object proportions;
- distinctive large objects;
- colors/materials;
- relative spatial relationships.

The POC does not require photorealism.

Primitive/procedural approximations remain acceptable when they communicate the correct object and room identity.

---

## 22. Gameplay Geometry

The AI-generated RoomDefinition must contain enough information for the existing RoomScale systems to derive:

- navigable floor;
- major floor obstacles;
- elevated navigable surfaces;
- surface elevations;
- valid approach areas;
- potential traversal relationships.

The reconstruction skill does not directly script civilization behavior.

It provides world data.

---

## 23. Elevated Surfaces

The reconstruction AI should identify major surfaces that reasonably function as tiny-civilization territory.

Examples:

- desk tops;
- table tops;
- dresser tops;
- cabinet tops;
- broad shelves.

A surface should not become navigable merely because it is technically horizontal.

The skill should favor surfaces large and coherent enough to matter at RoomScale's approximately half-inch citizen scale.

---

## 24. Traversal Information

The output must supply sufficient geometry or metadata for the generalized POC 1.5 traversal logic to derive a route opportunity.

The skill should not hard-code:

- a grapple build site;
- a lower anchor;
- an upper anchor;
- a scripted route;

unless the final POC 1.5 RoomDefinition contract explicitly requires that information as general room data.

The preferred model is:

**reconstruction describes the world → gameplay derives how the civilization responds to it.**

---

## 25. Output Contract

The final reconstruction output must use the same authoritative `RoomDefinition` format as POC 1.5.

Do not create a separate runtime format such as:

`PhotoRoomDefinition`

that requires a special gameplay path.

AI-generated rooms must enter RoomScale through the normal room-loading interface.

---

## 26. Inspectable Output

The generated RoomDefinition must remain text/data based and inspectable.

A reviewer should be able to determine from the artifact what the AI believed about:

- room dimensions;
- walls;
- doors/windows;
- major objects;
- object placement;
- appearance;
- navigable surfaces;
- obstacles.

Opaque AI state is not an acceptable replacement for the room artifact.

---

## 27. Validation

All AI-generated definitions must pass the normal POC 1.5 RoomDefinition validation layer.

Validation should catch at least the conditions already required by POC 1.5, plus any new POC 2 appearance/schema constraints.

The validator, not the AI, remains authoritative about structural validity.

A room must not be treated as successful merely because the AI produced syntactically valid-looking data.

---

## 28. AI Repair Loop

The reconstruction workflow must support:

**AI output → validator → structured errors → AI repair → validator**

The skill must explain how to perform this loop.

When validation fails:

1. preserve the AI's prior RoomDefinition;
2. capture validator output;
3. give both back to the AI;
4. instruct the AI to make the smallest appropriate correction;
5. rerun validation;
6. repeat within a reasonable attempt limit.

Do not repair invalid definitions by asking the user to edit JSON manually.

---

## 29. Runtime Independence

After a valid RoomDefinition is generated, the game must not require access to:

- Luna;
- ChatGPT;
- an OpenAI API;
- another hosted AI;
- the original photos.

The generated room becomes an ordinary RoomScale content artifact.

---

## 30. Model Independence

The skill must not contain Luna-specific hidden assumptions.

Luna may be the primary development/reconstruction model, but the artifact should be usable by another sufficiently capable multimodal AI.

The repository README should describe the requirement as a **capable multimodal AI**, not a mandatory proprietary model.

Model-specific notes may be documented separately when useful.

## 38. README User Workflow

The repository README must describe the end-user workflow clearly.

The workflow should be approximately:

1. Take several ordinary photos of one room from useful viewpoints.
2. Locate the RoomScale reconstruction skill in the repository.
3. Give the skill and photographs to a capable multimodal AI.
4. Ask the AI to create a RoomScale RoomDefinition.
5. Save the resulting room file in the documented RoomScale room directory.
6. Run the RoomScale validator/test command.
7. If validation fails, give the room file and validator output back to the AI for repair.
8. Launch RoomScale with that room definition.

The README must make clear that:

- four photographs are not required;
- measurements are optional;
- more useful views may improve results;
- the user is not expected to model the room manually.

## 43. Anti-Fake Requirement

POC 2 functionality must be genuine.

Permitted:

- approximate geometry;
- simplified meshes;
- procedural approximations;
- AI-estimated relative dimensions;
- generic material categories;
- selective omission of insignificant clutter;
- documented assumptions for unseen geometry.

Not permitted:

- manually authoring the canonical room and claiming the AI reconstructed it;
- giving the AI a hidden hand-written map of the canonical room;
- hard-coding canonical room coordinates in gameplay source;
- manually correcting object placement in Godot and treating the result as generated;
- using a specially prepared RoomDefinition that does not correspond to the AI output;
- bypassing the normal RoomDefinition validator;
- bypassing production gameplay in tests;
- declaring visual recognition successful without rendering the generated data.

The canonical room may be ugly.

It must actually be generated from the photo-driven workflow.

---

## 44. Failure Policy

When the reconstruction fails:

1. preserve the photos and original generated output;
2. capture the actual validator/runtime/visual failure;
3. identify whether the defect belongs to:
   - the skill;
   - RoomDefinition contract;
   - validator;
   - renderer;
   - RoomScale gameplay abstraction;
   - model capability;
   - insufficient photographic evidence;
4. correct the generalized layer responsible;
5. rerun from the appropriate point;
6. rerun existing Room A/Room B regression tests if shared contracts changed.

Do not fix a generalized reconstruction failure by adding a canonical-room special case.

If a model cannot perform the skill reliably, document the model limitation separately from deficiencies in the RoomScale architecture.

---

## 45. Definition of Done

RoomScale POC 2 is complete when:

1. the repository contains a reusable, self-contained room-reconstruction skill;
2. the skill teaches a capable multimodal AI how to convert ordinary room photographs into the established RoomDefinition contract;
3. the workflow accepts a variable number of photographs and requires no special scanning hardware or mandatory measurements;
4. Luna can use the skill and the canonical `photo_holder/` images to produce a valid RoomDefinition without manual room modeling;
5. RoomScale renders that output as a room recognizably corresponding to the source photographs;
6. the unchanged RoomScale simulation operates successfully inside the reconstructed room;
7. the complete elevated-terrain gameplay loop succeeds;
8. a fresh AI context can reproduce the reconstruction workflow from repository materials alone;
9. the skill is tested with a second capable multimodal AI/assistant where practical;
10. the README provides enough instructions for another user to repeat the process with photographs of another room.

The successful end state is:

**ordinary room photos → repository skill + capable multimodal AI → recognizable RoomDefinition → validation → unchanged RoomScale simulation → playable tiny civilization**

That is POC 2.
